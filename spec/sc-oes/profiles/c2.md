# SC-OES C2 Profile

**SC-OES C2 Profile v0.1.0 — Draft.** Profile maturity: `DRAFT`.

This document is complete for v0.1.0. Complete means every heading the specification requires of a
profile is written and says what this profile does and does not commit to — not that the profile has
acquired conformance rules of its own, which it has not; see "Conformance" at the end.

## Scope

Command and control, in one narrow sense for v0.1.0: the availability of the command,
control and communication systems an operation depends on. In scope is a change in a system's
represented availability. Out of scope are orders, tasking, unit reporting and the content of any
message a system carries.

Profile domain: `c2`.

## Version

```text
profile:         C2
profile_version: 0.1.0
sc_oes_version:  0.1.0
```

The profile version is independent of the SC-OES specification version and of every other profile's
version (`../01-core.md`). It moves when this profile changes and for no other reason.

## Maturity

```text
DRAFT
```

`../12-versioning.md` defines what each maturity value commits this specification to. A profile's
maturity is not inherited by the event types it names: each governed type carries its own maturity
in the packaged event registry, which is the machine authority for it.

## Ontology concepts

```text
c2:C2System                        a command-and-control system
c2:CommunicationSystem             a communication system
c2:SystemAvailabilityChangedEvent  the event class the governed type is annotated with
core:DependsOn                     what an operation does to such a system
```

The two system concepts are distinct because their outages are read differently: a C2 system's
unavailability suspends a decision path, a communication system's suspends a link. A producer that
cannot tell them apart annotates with `core:System` and says no more than it knows.

## Event types in scope

One governed type is in scope for v0.1.0, in the `c2` domain.

```text
sc.c2.system_availability_changed.v1
```

The authoritative list of governed types, with class, maturity, ontology class, payload model and
legacy mapping, is the packaged event registry
(`synapse_cdm/registry/sc_oes/event_types.json`). `../03-event-types.md` carries the human index,
which is where each type is paired with its class and maturity. This document names the identifiers
and nothing else about them, and MUST NOT become a second hand-authored copy: where it and the
registry could be read as disagreeing, the registry is right.

## EventClass

The types above span a single class, `STATE_CHANGE`.

A system becoming unavailable is a change in what is, and the profile keeps it
there. Whether the outage matters — to which mission, and how much — is an `IMPACT`, and the
Mission profile carries it. A C2 feed that graded its own outages would be making the judgement its
consumers exist to make.

## Payload semantics

No type in this profile has a registered payload model in v0.1.0. Payloads are free-form
and transportable. The example carries the system, the new availability, the previous one and the
affected service; the last is what lets a consumer tell a total outage from a degraded mode without
parsing prose.

## Required fields

This profile adds no required field of its own. An event in it carries what dimensions A
and B already require — the CDM's `event_id`, `event_type`, `severity`, `observed_at`,
`received_at`, `source` and at least one `source_ids` entry, and the SC-OES block's
`spec_version`, `event_class` and `type_id`.

## Optional fields

Every other field of the block is optional and absence asserts nothing
(`../01-core.md`). Conventions, stated as conventions and not as requirements:

- the previous availability SHOULD be carried, for the reason the Air profile gives;
- `status` SHOULD be set when the producer manages the outage as a condition with a standing, and
  left unset when it merely reports the change;
- `RESOLVES` SHOULD be used when a later event closes an earlier outage, rather than a second
  availability change that leaves the consumer to pair them (`../08-event-relationships.md`).

## Temporality

`observed_at` and `received_at` carry their ordinary meanings. A planned outage has a
window and uses `effective_from` and `effective_to`; an unplanned one ordinarily states neither, and
an absent `effective_to` does not mean the outage is permanent and does not mean it is still in
force (`../04-temporality.md`).

## Entity relations

`core:Concerns` for the system the event is about. `core:DependsOn` and
`core:Supports` are available for the relationship between an operation and the system, and a
producer that can support one may carry it; this profile requires none.

## Extensions

One bag, `oes.extensions`, keys `x.<namespace>.<name>`. This profile defines no extension and
reserves none. Availability vocabularies are vendor-specific almost everywhere — the same word
means "degraded" to one system and "unavailable" to the next — so a producer's own grading belongs
under its own namespace rather than in a field this specification would then have to define
(`../11-extensions.md`). The `sc.` prefix is reserved and undefined in v0.1.0 and is refused.

## Security considerations

A pattern of C2 availability events describes where a force is fragile, and the pattern
is more sensitive than any single event. Markings are transported and never enforced
(`../10-security-markings.md`); nothing in this profile makes one required.

## Examples

`examples/sc-oes/individual/sc.c2.system_availability_changed.v1.json` — one degraded system
with its previous availability and the affected service named, which is the pair a consumer needs
in order to tell a total outage from a partial one without parsing prose. It is loaded and
validated on every test run by `tests/test_cdm_examples.py`.

## Non-goals

This profile does not carry orders, tasking or unit reporting; it does not model network
topology; it does not define an availability taxonomy beyond the source's own words; and it does not
assess the operational consequence of an outage.

## Implementation status

**Specification-only in v0.1.0.** No adapter in this repository emits this profile's event
types. Every adapter this repository ships remains CDM Conformant without being an SC-OES semantic
producer, and that distinction is intentional (`../README.md`). Nothing in this tree should be read
as implying an operational adapter implementation exists for this profile: the examples under
`examples/sc-oes/` were written against the models by hand and name an adapter nothing resolves,
and PNT is the one profile with a reference producer behind it (`pnt.md`).

The profile's state, in the form the packaged registry carries it:

```text
Version:                      0.1.0
Maturity:                     DRAFT
Implementation status:        specification-only
Executable Dimension D rules: not defined in 0.1.0
```

A reader should not have to discover this from a `SKIP` on a command line. The packaged profile
registry (`synapse_cdm/registry/sc_oes/profiles.json`) carries the same four facts in the form a
validator reads, which is how a conformance tool tells this profile — known, and deliberately
without executable rules — from a profile name that does not exist.

## Conformance

Dimension D is assessed only against an explicitly named profile, and never inferred
(`../13-conformance.md`). This profile declares no conformance rules of its own in v0.1.0: every
constraint stated above is either one dimension A, B, C or E already checks — the CDM's structural
contract, the block's core syntax, the governed type's agreement with the registry, and the
recognition of governed ontology terms — or a convention marked SHOULD, which is guidance to a
producer and not a rule to grade against. A D assessment against this profile therefore
has no rules to check, and the permitted claim "SC-OES C2 Profile Conformant" is not yet
available. Dimensions A, B, C and E are unaffected: they do not depend on any profile.

The round that gives this profile its first rule of its own writes the rules and the check that
enforces them together, in the same commit — a dimension that reported a verdict no rule set could
change would be worse than an honest `SKIP`.

**Executable Dimension D rules for this profile: not defined in 0.1.0.** That is a scope boundary
and not an unfinished edge: `pnt.md` acquired the specification's first executable rule on
2026-09-07, and the arrangement stated just above is the one it followed. Until this profile does
the same, a dimension D assessment against C2 returns `SKIP` with a reason that says so, and
never `PASS` — a profile with no rules is not a profile anything can be conformed to — and never
`FAIL`, which would grade a profile for being deliberately specification-only.
